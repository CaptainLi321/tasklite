# 0009 产物授权、声明接纳与清理责任

状态：**Proposed（待用户裁决）**。本稿仅为 A1 设计，不授权实施 A2—A4；文中接口、状态和推荐行为均尚未实现。沿用 [ADR-0008](0008-trigger-contract-and-trusted-success.md) 的稳定 Job 身份、成功原子事务、执行锁与「未确认终态允许重做」边界，不选择新 IPC 传输。

本稿将删除授权、可写路径确认与未完成清理责任分开，避免声明失败后误删旧数据，或成功入库后才发现必要清理失败。需要用户裁决的行为集中于第 3 节的三个问题；第 2 节已经确认的规则不重新开放。

## 1. 当前事实与设计缺口

核验基线为 `main c0dcae2`：

| 入口 | 当前实现 | 本稿需要补齐的契约 |
|---|---|---|
| `JobContext.declare_output` | `cleanup_on_fail=True`，解析路径、创建父目录后返回；不拦截已有产物 | 三项独立授权、旧路径接纳、可写路径确认时点 |
| `JobContext.declare_cache` | 独立 `kind="cache"`；成功免存在检查，固定成败清理 | 统一声明值与薄封装，保留临时路径被 rename 的用法 |
| `ArtifactJournal.record_output` | worker 追加 JSONL、flush，写错被吞；没有父进程确认 | 接纳失败可观察，未接纳请求不得写入或获得删除权限 |
| `ArtifactJournal.cleanup` | 成功 cache 仅 unlink，失败目录 rmtree；错误可能被吞且声明文件仍被删除 | 文件/目录对称、失败责任不可丢失、删除前重新校验 |
| `CompletionMachine.complete_job` | 先业务终态提交，再 finally 清理 | 必要清理与终态提交的明确顺序 |
| 当前清理沙盒 | `output_roots` 与 `ipc_dir` 合并为删除信任根 | 业务产物授权与引擎通信目录分别管理 |

以上是待改变事实，不作为推荐方案的授权。源码入口：[context.py](../../tasklite/models/context.py)、[ipc.py](../../tasklite/utils/ipc.py)、[completion.py](../../tasklite/engine/completion.py)。

## 2. 已确认前提与术语

依据：[实施计划第 2、4 节](../IMPLEMENTATION_PLAN_2026-10.md)、[需求调研末尾确认项](../RESEARCH_TRIGGER_TIMING_2026-10.md#已确认方向未实施)。

- `delete_existing`、`delete_on_failure`、`delete_on_success` 分别表示前置删除、失败清理、成功清理，普通 output 默认均为 `False`，互不蕴含。
- 已有文件或目录而没有前置删除授权时必须报错。显式删除不承诺备份、恢复旧内容或跨产物的原子回滚。
- 目录声明代表整个目录及其内容，无额外递归开关；共享目录应声明专属文件或子目录。
- 声明及冲突检查必须早于该产物首次写入，允许 handler 中途动态声明，不要求启动前预枚举。
- cache 是 output 的薄封装，固定成败清理；前置删除仍独立授权，不保留独立 cache 类型或清理状态机。
- run 期间声明路径只由对应执行 Job 修改，其他程序和运行实例不得修改；消费方应正确声明 `depends_on`。不新增任务间内存 output、全套产物发布事务或 exactly-once 承诺。
- worker 已产生副作用但业务成功事务尚未提交时，恢复允许重做；本轮不新增持久化的未确认结果收件箱。保留同 uid 执行锁，孤儿 worker 存活时不得清理其产物或启动替代执行。

本稿使用三个不同概念：

- **删除授权**：调用方对指定路径及指定阶段作出的明确许可，不因路径位于沙盒内或存在声明日志而自动产生。
- **声明接纳**：引擎确认执行身份、路径边界与所有权无冲突，并可靠记录该请求；接纳本身不等于 worker 已获可写确认。
- **清理责任**：已接纳声明在相应终结阶段需要完成的删除义务；未履行时持续保留路径所有权，不能被新 attempt 覆盖。

## 3. 三项待裁决行为与候选比较

### 问题一：什么时候可写、清理失败时如何结束与恢复？

**推荐：持久接纳和前置删除完成后才确认可写；必要清理先于业务终态提交。**

| 选项 | 对用户可观察的行为 | 代价与限制 |
|---|---|---|
| **推荐：严格确认，先清理再提交** | 声明确认失败时不返回可写路径；环境性接纳/清理失败使 run 抛错、保留候选和清理责任，不消耗 handler 重试预算，不伪报成功 | 可能阻塞整次 run；崩溃后必须先处理清理责任，尚未确认的业务可能重做 |
| 持久接纳，先提交终态再清理 | Job 可已成功或失败，但 run 因后续清理失败报错；持续保存独立清理责任，不能再把已成功 Job 登记为失败 | 用户必须理解「业务已终结但清理未完成」；管理查询与恢复需表达该差异，不再是统一的提交前门槛 |
| 仅尽力写 worker 日志后继续 | 可能先写业务文件，再被父进程发现记录缺失或路径冲突 | 不满足未接纳不写、失败可观察的目标，不推荐沿用 |

**推荐方案的接纳顺序**：

1. worker 提交路径、三项授权和执行身份。父进程检查执行仍有效、路径及根保护、同路径/重叠冲突；此时不改业务路径。
2. 持久记录该执行的排他预留及前置删除意图，再允许前置删除。该记录属于已接纳的控制状态；若记录失败，不删除旧内容、不返回路径。
3. 已有对象仅凭 `delete_existing=True` 删除；前删前须确认叶对象仍是接纳时记录的旧对象，或路径已经不存在，不能将被替换的新对象当作原授权目标。此前 `delete_on_failure` / `delete_on_success` 尚不成为旧内容的清理权限。若删除部分完成后失败，不承诺恢复被删内容，保留前置删除责任并停止本次 run。
4. 路径确认不存在且父目录准备就绪后，持久记录可写确认及后续清理授权，再向 worker 返回规范绝对路径。未收到确认，worker 不得开始写该路径。
5. 崩溃发生在记录可写与 worker 收到确认之间时，恢复保守按已确认声明处理；不得把不确定是否写入解释为可以丢弃清理责任。

**推荐方案的终结与恢复顺序**：

- handler 成功：先验证需保留的产物，再完成 `delete_on_success=True` 的必要清理，全部完成后才经 `CompletionMachine.complete_job` 的成功事务提交 successes、成功 Attempt、queue/failed 移除、spawn/cursor。
- handler 失败、故障重试或中断：只对已获可写确认且 `delete_on_failure=True` 的路径清理；完成后才提交相应失败或重入队。瞬态仍不烧预算、不污染失败档案。
- 环境性接纳或清理失败：错误直接归于 run 的基础设施路径，保留当前候选及原 `activation_no / attempt_no / max_retries`，不伪装成 handler 失败，不推进故障重试预算。若 handler 原本已失败，原业务重试也须等待清理门槛完成，不能以再次执行 handler 代替清理。
- 重启先排除仍活跃的执行锁，再处理持久前置删除/清理责任；责任未完成时阻止该 uid 的新 handler、后续声明及冲突路径接管。环境仍不可用则继续明确报错，不能忙旋重跑业务。
- 当前进程仍存活时可以保留已解析结果，待清理完成后使用同一结果提交；跨进程崩溃不保证保存该结果。若未提交结果已经丢失，先完成所有既有责任，再重新执行未确认 Job；重复副作用是此选择的明确成本。
- 不引入持久结果收件箱。若要求「清理失败后无论如何都不能重做 handler」，须重开 ADR-0008 的恢复裁决，不能作为本方案的隐含保证。

### 问题二：哪些文件、目录和链接可以授权，删除时如何确认没有越界？

**推荐：拒绝声明叶节点符号链接（含断链）；父目录链接先规范化并校验，删除时必须再次校验身份与边界。**

| 选项 | 行为与取舍 |
|---|---|
| **推荐：叶链接拒绝、父目录规范化后接纳** | 普通文件和目录可声明；叶链接不解释为目标删除许可；父级合法链接仍可支持常见目录布局，但必须返回规范路径并复核 |
| 所有层级链接均拒绝 | 删除规则更简单；会拒绝正常的链接目录布局及部分平台的默认路径布局 |
| 跟随叶链接作为目标声明 | 更接近当前 resolve 行为；用户以为声明链接本身时可能实际授权删除目标，断链与重定向更难解释，不推荐 |

**推荐路径矩阵**：

| 路径情形 | 推荐接纳与删除行为 |
|---|---|
| 不存在的普通路径 | 校验规范父路径与冲突后接纳；不存在不自动创建目录产物，仅创建必要父目录 |
| 已有普通文件 | 无前置删除授权报 `FileExistsError`；有授权且接纳可靠记录后才删除 |
| 已有空目录或非空目录 | 同文件规则；目录授权覆盖整个目录，不另加递归开关 |
| 声明叶节点为符号链接或断链 | 拒绝，不删除链接或其目标；不能先 resolve 丢失叶链接事实再接受 |
| 父目录含链接且规范目标仍在允许范围内 | 接纳规范路径并记住校验依据；worker 必须使用返回路径 |
| 父链接越界、解析循环、无法确定对象类型 | 拒绝，不退回仅做 abspath 后继续删除 |
| 目录内部有符号链接 | 删除目录时只移除链接本身，不跟随到目标 |
| 目录内部有挂载点、平台重解析点且无法证明不会遍历边界 | 拒绝递归删除并保留责任，不能按普通子目录盲目穿越 |
| 规范化后等于文件系统根、盘符根或网络共享根 | 始终拒绝作为业务产物 |
| 等于任一配置 `output_roots`，或目录声明覆盖任一输出根 | 拒绝；各根下的专属后代可按其余规则声明，不能通过外层目录删除其他输出根 |
| 位于状态目录或 IPC 目录内（含目录本身和全部后代），或目录声明覆盖它们 | 始终拒绝作为业务产物；不允许把引擎内部文件伪装为 cache，`sandbox=False` 也不豁免 |
| 无 `output_roots`，或显式 `sandbox=False` | 可接纳具体路径，三项授权仍独立；不豁免上述根保护、所有权冲突与删除复核 |
| 多输出根 | 相对路径仍按首个根重定位，绝对路径可落在任一根；任一根及其祖先均受保护 |

前置删除和后续清理都必须在每次操作前重新确认：执行身份与所有权仍有效、授权仍覆盖当前动作、父目录对象没有被替换、规范路径仍符合接纳时范围、叶节点不是不允许的链接。检测到父目录替换、沙盒漂移或对象类型异常时停删并报错，保留责任。

路径身份不是单次 `resolve()` 的证明。实现须在可支持的平台使用不跟随链接的对象检查与目录定位操作，使检查依据与实际删除对象绑定；无法保证时明确拒绝该操作，不宣称全平台都具有同一原子性。声明叶节点原本不存在，后续由所属 worker 创建或 `os.replace` 成普通文件是正常写入；不能一概以最终文件 inode 改变拒绝合法原子产出。父目录身份替换与所属 Job 的合法叶文件替换须分别测试。

本方案不把「其他程序不得并发改动」的调用前提扩大为可抵御任意恶意并发篡改的安全边界；已检测到的替换也绝不能忽略或继续按新目标删除。

### 问题三：重复声明、目录重叠和所有权什么时候允许接管？

**推荐：同执行同路径同权限幂等，其余活跃重复或祖孙重叠拒绝；旧责任完成后才能接管。**

| 选项 | 行为与取舍 |
|---|---|
| **推荐：严格排他与幂等重复** | 同一执行的相同声明可重复调用，不二次前删；改权限、跨 uid 同路径及祖孙重叠均拒绝，便于确定谁可以删 |
| 同 Job 权限取并集、允许父目录包含子声明 | 声明更灵活；重复调用可能扩大删除范围，目录与子文件责任叠加，清理及升级顺序更复杂 |
| 同路径后声明覆盖前声明 | 接口短，但会让较晚声明改变已写产物权限或夺取其他 Job 的路径，不推荐 |

**推荐冲突矩阵**：

| 已有状态与新声明 | 推荐行为 |
|---|---|
| 同一执行、同规范路径、三授权和范围完全相同 | 幂等返回同一路径；即使当前已写入，也不因路径已存在再次拒绝或前删 |
| 同一执行、同路径但权限或范围不同 | 拒绝升级、降级或覆盖，既有接纳记录保持原样 |
| 同 Job 的不同 attempt/执行代，旧声明尚未释放 | 拒绝以新声明覆盖；先恢复旧责任并确认旧 worker 已退出 |
| 活跃不同 uid 声明同一路径 | 拒绝后来的声明，不隐含排队或调度顺序 |
| 任意活跃声明之间有祖先/后代关系 | 拒绝，包括同 Job 的目录与内部文件；改为只声明目录或只声明专属文件集合 |
| 兄弟路径，如 `result.part` 与 `result` | 可各自声明，分别授权；适用于临时文件原子 rename |
| 旧 Job 终态已提交且清理责任全部完成，保留文件仍在 | 排他预留可释放；后来不同 Job 仍需 `delete_existing=True` 才可显式接管，不继承旧 Job 的任何删除权限 |
| 只存在历史 successes/failed 记录 | 不构成永久文件占有权；但物理路径存在检查与当前活跃声明冲突照常执行 |

所有权由受控接纳、确认、清理和释放入口维护，以执行身份区分同 uid 的不同执行代；不能只用路径日志的最后一行或单独 uid 判定当前所有者。预留从持久接纳开始，直至必要清理完成且该执行的失败/重入队/成功转移已可靠提交后释放。未完成责任跨 run 保留，不能由 PRE_SUBMIT 清空、清历史或新 Job 快照覆盖而消失。

这里的冲突表约束可写产物声明，不新增输入路径的全局独占注册，也不自动发现消费者。上游产物可在其声明释放后供下游作为 input 使用；调用方仍须用依赖与独占写入前提避免其他 Job 写入正在使用的输入。

## 4. 拟议公开签名与 cache 等价规则

待三项裁决批准后才可实施：

```python
def declare_output(
    path: str | Path,
    *,
    delete_existing: bool = False,
    delete_on_failure: bool = False,
    delete_on_success: bool = False,
    sandbox: bool = True,
) -> str: ...


def declare_cache(
    path: str | Path,
    *,
    delete_existing: bool = False,
    sandbox: bool = True,
) -> str: ...
```

拟删除 `cleanup_on_fail`，无别名、无双写。cache 精确等价于 `declare_output(path, delete_existing=..., delete_on_failure=True, delete_on_success=True, sandbox=...)`；底层声明值不保存独立 cache kind。

为保留该等价和已 rename 的临时路径用法，推荐统一规则：`delete_on_success=False` 的保留产物在成功前必须存在；`delete_on_success=True` 的临时产物可已不存在，存在时必须完成成功清理。该规则同样适用于普通 output 的同一授权组合，不能只给 cache 设置隐藏特例。

典型顺序为：先声明不存在的最终路径，再声明临时兄弟路径并写入，最后 `os.replace(tmp, final)`。若最终路径原已存在，必须在其声明上独立传入前置删除授权；临时路径的权限不能授权删除最终路径。

## 5. 故障责任与恢复验收矩阵（推荐方案）

| 故障窗口 | 必须保留的事实与后续行为 |
|---|---|
| 路径或权限校验失败、冲突拒绝 | 不接纳、不写该路径、不产生该请求的新清理权限；既有声明不变，错误可由 handler 观察 |
| 持久预留失败 | 不删除旧内容、不返回可写路径；基础设施错误停止 run、保队，原预算不变 |
| 已预留但前删失败或进程死亡 | 保留前删意图及旧对象核验信息；后续清理权限尚未对旧内容生效；恢复先核验执行锁与路径，再继续前删或明确报错 |
| 前删完成但可写确认记录失败 | 不确认 worker 可写；持久责任不能遗失，也不承诺恢复被显式删除的旧内容 |
| 已持久确认但回复丢失、worker 被强杀 | 以接纳记录和执行锁为准；对已确认路径只应用独立失败清理授权，不凭日志缺少最后一行推导无责任 |
| 成功清理失败 | 不提交新的业务成功、不写 handler failed；保队并持续保存责任，未处理前禁止再次执行 handler |
| 失败/重试/中断清理失败 | 不为清理故障推进预算、不伪造业务终态；保留责任并停止 run，先恢复清理 |
| 清理完成但成功事务失败 | queue 与历史业务事务按现有原子契约保持；责任释放须与提交事实一致。跨崩溃结果丢失可重做，不恢复已删除内容 |
| Job 终态已提交但释放记录未完成 | 恢复核验已提交终态后幂等释放，不重新执行已确认成功的 Job，不重新前删 |
| 清理时发现父目录替换、越界或不允许的链接 | 停删、报错、保留责任及当前对象，不沿新目标继续操作 |
