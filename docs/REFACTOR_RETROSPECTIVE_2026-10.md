## 2. 讨论从文档整理扩张到架构重建

最初目标是保证信息不丢失，降低文档阅读成本。Gemini 提出了 ADR 索引、主题聚合、生命周期矩阵、不变式索引和指南重排。

其中有价值的部分：建立入口、明确适用范围、消除重复叙述、让基础模型先于高级编排、把 Job 改名从失败治理中分离，把存储编码移到存储章节。ADR 原文稳定引用有助于追溯。

需要克制的部分：索引不应复制全部规范形成第二份真相源；不能仅按编号推定 ADR 有效性；统一元数据和复杂状态矩阵是否必要，应由实际维护成本决定。“信息量不变”要求保存动因、不变式、边界及重开条件，而不是机械保留每段历史文字。

用户随后允许核实一致性后删除历史 ADR，要求删除 v1 历史文档、依赖与动态报告计划，将 Discovery 长注释迁入 ADR。讨论又延伸到 ADR-0009、身份编码、IPC、生命周期、重试、产物覆盖与框架选型。

复盘问题：原本的文档整理没有持续保持范围边界，多个独立设计问题相互牵引，最终演变为未经真实下游验证的系统重构。下一轮应按问题立项，分别验证，不能靠一份越来越大的 ADR 同时解决所有问题。

## 3. 身份编码与文件名：问题存在，但复杂度来源值得重审

### 3.1 曾提出的职责拆分

- 逻辑 UID：区分 Task 类型与调用方 JobID，组合边界必须明确。
- 组合 JobID：供业务或 Discovery 组合多段标识，避免手工拼接碰撞。
- 文件投影：适配操作系统文件名规则，不应反过来定义业务身份。
- 展示文本：尽量可读，但不能承担唯一性。

用户希望 Unicode 和 JobID 尽量可读，允许不向前兼容，曾接受“可读前缀 + 完整 Base32 可逆尾段”。后续实现涉及规范编码、schema 升级、Unicode 正规化、大小写不敏感文件系统、组件长度预算及多种 IPC 后缀。

### 3.2 不同方案的取舍

| 方案 | 收益 | 代价或限制 |
|---|---|---|
| 百分号可逆转义 | 部分原文可读、可以反解 | 需处理平台保留名、大小写与长度、规范形式 |
| 可读前缀 + 完整 Base32 | 展示与身份分离，尾段无损 | 文件名变长，前缀/尾段/后缀预算及正规化协议复杂 |
| 净化非法字符 | 直观、便于生成展示名 | 不同输入可映射到同名，不能直接作为唯一身份 |
| 有限摘要 | 短、易适配路径 | 不是数学上的单射，也不能无损反解 |
| 去掉每 Job 文件 IPC | 减少文件投影需求 | 必须重新解决通信、进程退出、恢复与提交顺序 |

Gemini 推荐 yt-dlp 的 `sanitize_filename`。值得借鉴其跨平台文件名经验，但项目流行度不构成契约适配证据：生成可用展示名与保存可逆唯一身份是不同目标。不能未经许可证、依赖、辅助逻辑和实际契约核实就复制函数，更不能把净化函数当作 Job 去重编码。

本轮编码方案已随回退撤销。保留的教训是：先确认哪些功能真的需要动态文件名，再决定文件投影协议，避免为了 IPC 实现细节扩张整个身份模型。

## 4. 引擎为何写文件，哪些状态必须持久化

此前调研的重构工作区中，文件涉及：结果传输、声明记录、运行时信号及其回收中间态、执行锁、流水线锁，以及 SQLite 状态。Job 启动参数通过 multiprocessing 传递，并非每个 Job 都存在输入 payload 文件。

必须区分三类职责：

- **持久业务调度状态**：待执行任务、成功/失败记录、必要游标与恢复信息。进程退出后仍有价值。
- **执行通信**：子进程结果、声明、限流等信号。不能仅因当前实现落盘，就把它们认定为业务持久数据。
- **业务产物**：用户文件、数据库写入、远端服务副作用。不是引擎 IPC。

当时发现的维护负担包括：临时写入和替换、run token 校验、陈旧结果、JSONL draining、文件后缀长度、锁 inode 生命周期、清理失败与孤儿进程。SQLite 与 IPC 文件也不能天然组成一个原子事务。

当前用户方向是取消文件 IPC。Pipe、Queue、连接或其他通信机制只是候选，不在本文中择定。后续至少需要验证：

1. 子进程完成发送但父进程提交前崩溃，恢复后是否允许再执行？
2. 父进程先退出、worker 未退出时，谁持有执行互斥与回收责任？
3. 大结果、背压、关闭顺序、超时强杀是否死锁或丢消息？
4. 声明和运行时信号能否合并为窄通信协议？
5. 哪些锁仍必须跨进程或跨运行存在？取消 IPC 文件不自动等于可以取消所有锁。

不能承诺取消文件就得到 exactly-once。外部副作用完成而引擎未记账，是独立的提交边界问题。

## 5. Job、Attempt 与完成语义

用户希望框架只看到一次运行的成功或失败，不让业务 Job 手工向父进程提交结果。结果传输及收尾应由框架管理。

需要保留的区分：

- Task 是执行规格，Job 是逻辑工作，Attempt 是一次执行的观测记录。
- “一次执行的终结只有成功/失败”不等于系统不需要排队、运行、重试等待等调度事实。
- 引擎执行成功表示 handler 满足其执行契约，不代表批次中每个业务对象都成功，也不代表所有外部副作用具备原子性。
- Attempt 可以记录重复执行，不应为了每次重跑强迫业务变更逻辑身份。

此前工作区调研还指出：“六集合互斥”的表述实际涉及 queue、in_flight、wall、failed 的两两关系，不能据此凭空列出六种 Job 状态；重跑时既有成功事实与新执行的关系更需要明确定义。

当时 Attempt 实现包含开始记录和终结更新，并非每一步都是不可变追加；部分代码还依赖历史记录分配执行标识。因此“Attempt 只是日志”是职责期望，不能直接据此删除其存储或裁剪历史。

## 6. 身份、确定性与重跑：观点如何变化

### 6.1 身份不等于确定性

用户提出，同参数 Job 结果一致，框架只按 JobID 判断是否同任务。讨论倾向于由调用方定义稳定身份；Task 类型是否构成身份命名空间应保持明确。

下游证据修正了“相同参数必定相同结果”的普遍假设：网络、数据库、模型、代码和文件都可能是隐式输入。引擎可以只按身份去重，但不能仅凭身份承诺结果确定性。某个 Task 可以自行承担更强的纯函数契约。

### 6.2 被提出后撤回的方案

曾建议把重试、定时或文件变化触发移到 wrapper，以类似 `A::transcode_rerun_time_...` 或 `B::find_rerun_filechange_...` 的新 ID 表示执行。

用户指出：事件序号需要额外持久状态，毫秒时间和摘要也不是免费、无歧义的语义；引擎已有每次运行重跑的需求。不断换 ID 会增加历史、依赖、输出归属的维护负担。该方向最终撤回，不应继续作为默认设计。

### 6.3 当前方向

**引擎负责重跑，外部负责判断触发条件。** 文件变化、时间、业务事件、人工强制等条件可以由外部定义；不把具体文件探测实现固化为引擎职责。

后续需分别定义：失败后的 retry、成功后的 rerun、进程中断后的 recovery。它们可以共享执行机制，但预算、触发与依赖语义不应含混。

trigger 接口尚未定稿，需要回答：在何时求值、是否需要保存外部检查点、触发器异常如何处理、重复触发如何合并、运行中触发是否排下一次，以及下游依赖的是历史成功还是本轮成功。本文不预设额外事件序号或新调度 seam。

## 7. 输出声明、覆盖与清理的争论

观点依次经历了：

1. 用户指出已有输出声明和失败自动清理，无须重新发明半成品管理。
2. 用户要求声明在 Job 启动前完成；预先存在输出应报错；清理失败应直接报错，可能代表外部冲突或设计问题。目录声明已有支持。
3. 重跑场景暴露冲突：成功输出必然可能存在；要求永不存在旧输出会使正常重跑难以维护。
4. 用户接受覆盖，但明确反对因此在启动时自动递归删除旧目录；误填根目录会把原先的及时失败变成破坏性操作。

因此，“存在即报错”不能再当作适用于所有重跑的最终契约；“允许覆盖”同样不等于授权任意递归删除。

需要分别考虑：

| 对象 | 可能的契约 | 未决问题 |
|---|---|---|
| 本次创建的私有临时空间 | 失败时可清理 | 如何验证所有权、处理符号链接和孤儿 worker |
| 昂贵中间检查点 | 失败后保留供续跑 | 完整性、失效和回收责任 |
| 已成功发布的产物 | 新结果成功后替换或保留版本 | 多文件与数据库间如何一致提交 |
| 用户指定的既有目录 | 声明不自动授予全部删除权 | 混合内容、共享目录、路径错误 |

预声明有助于提前验证，却不能单独证明所有权；输入和输出也可能是运行时发现的。把所有业务限制成预先枚举路径，需要先用真实场景验证。

曾发现的实现问题包括声明持久化错误被吞、终态提交后才清理、目录与 cache 清理不对称、多个 UID 输出重叠未统一处理。它们是后续调查线索，不应借此未经设计就新增一整套发布事务。

## 8. 同类引擎给出的不同答案

本次查阅过官方文档和源码，以下用于说明设计选择，不能代替迁移原型，也不代表这些工具解决全部业务问题。

| 引擎 | 相关设计 | 对本讨论的启发 |
|---|---|---|
| Luigi | Task 身份来自任务族和 significant 参数；默认按输出存在判完成；LocalTarget 提供单文件原子写入 | 身份与输出完成判定分开；多文件和数据库事务仍需应用处理 |
| Airflow | 同任务实例可以多次尝试；不同 DAG Run 表示不同运行 | 不必用改任务 ID 表示 retry；副作用幂等通常由任务作者承担 |
| Nextflow | 任务工作目录与发布目录分开；resume 结合缓存和输出检查 | 私有工作空间可减少覆盖风险，但缓存/发布仍有协议成本 |
| Snakemake | 显式声明目录输出，并按其所有权契约清理 | 自动删除依赖强所有权假设，不是声明任意路径就安全 |

- Airflow：[任务](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html)、[重跑](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dag-run.html#re-run-tasks)、[任务幂等建议](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html#creating-a-task)。

## 9. 真实下游调研

实际下游以稳定匿名代称记录，不保留项目名称、本地路径或可定位的源码入口。调研为只读源码分析，未运行业务或复现列出的问题；2026-10-23 的文件布局和观察不保证此后不变。简单爬虫下载项目没有提供源码，不能替它们推定需求。

### 9.1 文献处理项目（项目A）：嵌入式执行与业务存储分离

项目包含根旧版、中间版和新版三代代码。根旧版依赖 1.2.0 系列接口，中间版声明至少 2.0.0，新版声明至少 2.1.0。新版 editable 安装直接指向 TaskLite 工作区，安装元数据不是源码冻结证明。

新版实际使用持久队列、静态 DAG、API 限流、容量、超时、失败重试、Selection、Attempt hook 和设备间状态接力。跨设备是单活租约与快照交接，不是远程多机 worker 调度。论文去重和业务进度另存业务库。

新版没有发现实际调用 Discovery、declare_output、declare_cache 或输入变化重跑；它预生成 DAG，并在 handler 运行时查库。为本轮新 PDF 设置转换清扫批，说明工作集合的动态变化由业务补偿。

产物由业务管理：PDF/MD 使用私有临时目录、校验、CAS 归档，再更新业务指针；失败清理本次沙盒。报告使用输入/模型/协议指纹、独立状态目录和检查点，保留昂贵中间结果。Zotero 副作用依靠业务台账和内容检查保证重复执行安全。

旧版曾实际使用输出声明、固定 UID every_run 和清理历史的绕行；这些不能混算为新版现状。新版快照直接依赖 TaskLite SQLite 表和路径字段，是明确的内部接口耦合。批量任务可能吞掉单篇失败并返回整批成功，进一步说明引擎成功与业务对象成功不同。

主要源码调查范围：新版引擎装配、任务生成、PDF 获取与转换、内容寻址存储及报告执行模块。

### 9.2 实验处理项目（项目B）：文件驱动的静态实验 DAG

调研范围为流水线及其所属项目的开发规范。代码使用 `add_resource`、`register_handler`、`TaskContext` 等旧 API；调研发现系统安装元数据为 1.2.0，未见项目内版本锁定。不能视为当前 2.1.0 的兼容验证。

流程为 imaging → cfar → filter → track，门控另接 parity。调用方按参数生成键并去重上游节点；MATLAB 执行、实验目录、SQLite 状态、容量控制、成功跳过和重试都有实际用途。没有发现 Discovery、动态扩图、every_run、on_input_change 的实际使用。

文件直接写最终路径，主要结果声明失败清理，日志保留。额外 CSV 和部分输入未声明，可能产生新旧文件混用。成像依赖实验目录外的共享缓存，实验并非完全自包含。

静态风险线索：

- gate 使用 on_failure，历史成功可能跳过本轮验证；入口未核对任务失败就打印成功。
- 成像缓存缺失时，装配给定路径与 handler 实际输出路径不一致；现成缓存可能掩盖该问题。
- 参数或代码改变但身份未变时，没有自动失效契约。
- 归档补测明确绕开旧 wall 中的绝对路径，直接检查现有文件并只入队 Track。

主要源码调查范围：实验与流水线入口、任务处理、实验配置、一致性校验及 MATLAB 分步执行模块。以上是调查线索，不是已经修复或运行复现的缺陷。

## 10. 是否重复造轮子，以及前期调研的不足

队列、重试、锁、恢复、依赖和文件完成判断都属于成熟领域，TaskLite 确实重复实现了部分机制。两个下游在用它，只能证明有这些需求，不能证明自研优于成熟工具。

项目B 与 Luigi 的文件 Target、参数化任务和静态依赖较接近；前期应更早验证。项目A 的资源限制、设备准入、业务存储和快照接力是否容易适配，需要实测，不能仅靠功能名称下结论。

讨论曾建议用项目B 的一个完整分支做对照原型，验证共享节点、失败重试、中断续跑和产物覆盖。该建议未实施，也不是本次回退之外的自动执行授权。

框架边界的候选定位是“嵌入式持久任务执行库”：保持运行和恢复能力，让业务拥有领域缓存、产物发布及副作用。是否最终采用这一定位，仍应由迁移成本和真实需求验证，不能用沉没成本作决定。

## 11. 下一轮设计的检查清单

1. 先固定重跑职责：引擎执行，外部 trigger 判断；明确与 retry、recovery 的关系。
2. 先列 IPC 必须传输的信息和故障窗口，再选传输机制；不以文件残留协议作为默认起点。
3. 把输出声明、路径所有权、覆盖、失败清理、成功发布拆开讨论；不由 JobID 自动推导删除权限。
4. 不把 Job 身份、业务输入指纹、文件名、Attempt 标识合成一种编码职责。
5. 用项目A 和项目B 的具体流程验证接口；旧版与新版证据分开。
6. 对稳定身份重跑后的依赖语义给出明确例子：下游何时能使用旧成功，本轮上游失败时如何处理。
7. 若要支持状态快照/迁移，先评估实际需求，避免下游继续直改 SQLite 内部表。
8. 在新 ADR 中明确“已决定、待验证、未实施”，只记录单个可审查决策。本文保留争论，不代替这些 ADR。

本轮最重要的收获是识别职责混淆：重跑不等于换身份，声明不等于删除授权，执行成功不等于业务事务提交，IPC 不等于持久业务状态。回退实现不需要丢弃这些认识。
